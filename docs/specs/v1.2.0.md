# Build Prompt: template v1.2.0 — Collections, Global content, Forms

How to use: put this file into the template repository as `docs/specs/v1.2.0.md`, open
Claude Code in the repo and say: "Read docs/specs/v1.2.0.md fully and implement it. Start
in plan mode."

## 0. Role and rules

You are extending the web-admin-panel site starter. The repo's `CLAUDE.md`, `docs/SPEC.md`,
`docs/ARCHITECTURE.md`, `docs/CONTENT_SCHEMA.md` and `docs/DECISIONS.md` define how this
codebase works; read them all before planning. Everything below must follow the existing
patterns (field builders, registry, cached loaders with tags, generated admin forms, server
actions with `runAction` + `assertPermission` + Zod + audit log, proxy without DB access,
design tokens, e2e on a production build).

1. Plan mode first. Produce a plan split into the phases in §6, then implement.
2. Read current docs for Next.js 16 (`node_modules/next/dist/docs/`), Drizzle, Better Auth,
   next-intl before using an API. Don't rely on memory.
3. Reuse, don't duplicate. The page editor, revisions, conflict detection, media pipeline,
   SEO tab, locale dropdown, rich text, validation and cache tagging already exist. New
   features must reuse them through shared modules, not copies. Refactor the existing code
   into reusable pieces where needed, keeping behavior and tests green.
4. Core vs project boundary stays intact: definitions live in the project layer
   (`src/content/**`), engines in the core. `src/core` and `src/admin` never import
   `src/site`.
5. Backward compatible. A project on v1.1.0 that defines no collections, globals or forms
   must work unchanged after merging v1.2.0 (no required config, migrations are additive).
6. Admin main sidebar stays exactly: Overview, Pages, Managers, Settings, Security, Sign
   out. New editing UI lives inside Pages (secondary sidebar groups) and Settings.
7. Commit after each phase with green gates (`typecheck`, `lint`, `test`, `content:check`,
   `tokens:check`; `e2e:prod` for routing/caching/security changes). Record decisions in
   `docs/DECISIONS.md`. English everywhere.
8. Public API names below are fixed (the `site-from-design` skill relies on them):
   `defineCollection`, `defineGlobal`, `defineForm`, `getCollectionList`,
   `getCollectionItem`, `getGlobalContent`, and the registry accepting collections, globals
   and forms.

## 1. Registry

Extend `createRegistry` to accept pages plus optional collections, globals and forms, e.g.:

```ts
export const registry = createRegistry({
  pages: [homePage, aboutPage, blogPage, contactPage],
  collections: [blog],
  globals: [siteGlobals],
  forms: [contactForm],
});
```

Keep the old array form working (`createRegistry([...pages])`). Validate unique ids across
each kind, path conflicts between pages and collection item paths, and references (a
collection's `listPageId` must be a registered page).

## 2. Collections

### 2.1 Definition (project layer)

```ts
// src/content/collections/blog.ts
export const blog = defineCollection({
  id: 'blog',                    // stable DB key, kebab-case, never renamed
  label: 'Blog',                 // admin group label
  itemLabel: 'Post',             // "New post"
  listPageId: 'blog',            // registered page that renders the list (/blog)
  itemPath: '/blog/:slug',       // must start with the list page path
  fields: {                      // same f.* builders as pages (no sections level)
    title: f.text({ label: 'Title', required: true, max: 120 }),
    excerpt: f.textarea({ label: 'Short description', max: 300 }),
    cover: f.image({ label: 'Cover image', localized: false, recommendedSize: '1600×900' }),
    body: f.richText({ label: 'Text', required: true }),
  },
  titleField: 'title',           // used for admin table, default SEO title, slug suggestion
  summaryField: 'excerpt',       // optional: default meta description
  imageField: 'cover',           // optional: default OG image
  sort: { by: 'publishedAt', direction: 'desc' },   // or a field name
  pageSize: 12,
  missingTranslation: 'fallback',   // 'fallback' to default locale | 'hide' in that locale
  structuredData: 'BlogPosting',    // 'Article' | 'BlogPosting' | 'NewsArticle' | none | function
  seed: [ { slug: 'hello-world', publishedAt: '2026-01-15', content: { en: {…}, uk: {…} } } ],
});
```

Types must be inferred from `fields` exactly like pages (no manual types on the site).

### 2.2 Data model (Drizzle, additive migration)

- `collection_items`: id, collection_id, slug, status (`draft | published`), published_at,
  version (optimistic concurrency), created_by, updated_by, created_at, updated_at. Unique
  `(collection_id, slug)`. Indexes for list queries `(collection_id, status, published_at)`.
- `collection_item_content`: item_id, locale (or `_shared`), data JSONB, version, timestamps.
- `collection_item_seo`: item_id, locale, same shape as `page_seo`.
- `collection_item_revisions`: last 20 per (item, locale), same as page revisions.
- `collection_slug_redirects`: collection_id, old_slug → item_id (slug changes keep old URLs
  working with a 308 redirect).

Slug: lowercase, `[a-z0-9-]`, max 100, unique per collection, suggested from the title in
the default locale (transliterate Cyrillic), shared across locales.

### 2.3 Admin (inside Pages)

- Pages secondary sidebar gets groups: Pages (existing tree), Collections (one entry per
  collection with item count), then Site-wide and Forms (§3, §4). Search filters all groups.
- Collection screen: data table (title in the default locale, status badge, publish date,
  per-locale completeness, updated by/at), search, status filter, sort, pagination, New
  {itemLabel} button.
- Item editor reuses the page editor: locale dropdown, Content and SEO tabs,
  unsaved-changes guard, revisions drawer, conflict detection. Extra panel: slug (with
  suggestion and uniqueness check), status (Draft / Published), publish date, "View" link
  (published) or "Preview" (draft, staff only), Delete (confirmation).
- Permissions: managers and admins can create, edit, publish, unpublish and delete (same as
  page content). Every mutation: `assertPermission`, Zod, audit log entry with readable
  target (collection label + item title).

### 2.4 Site

- `getCollectionList(collectionId, locale, { page })` → `{ items, page, pageCount, total }`
  with typed, resolved items (images resolved, title, slug, href, publishedAt), only
  published.
- `getCollectionItem(collectionId, slug, locale)` → typed item or `null`.
- Helper `createCollectionItemRoute(collectionId, View)` analogous to `createPageRoute`:
  `generateStaticParams` for published items × enabled locales, `generateMetadata` (item SEO
  → item defaults → site defaults), localized 404 for unknown/draft slugs, 308 for
  redirected slugs, staff draft preview.
- Cached with `'use cache'` and tags `collection:{id}`, `collection:{id}:{slug}`,
  `collection:{id}:list`; saving/publishing/deleting revalidates only affected tags plus the
  sitemap. Pages stay static/ISR.
- List pagination with real URLs (`/blog?page=2`), `rel="prev"/"next"` not needed, but each
  page has a self canonical; page numbers beyond `pageCount` → 404.
- The proxy's known routes include every collection `itemPath` (from `/api/site-state`) so
  item URLs are not 404'd by the gate. `content:check` validates that the list page and the
  item route file exist.
- Sitemap: published items per enabled locale with hreflang alternates and `lastModified`;
  excludes `noindex` items and hidden translations.
- JSON-LD per `structuredData`, plus BreadcrumbList (Home → list page → item).
- Analytics: item views attributed to the collection item (path + collection id).

### 2.5 Tooling

- `content:sync` seeds collection items from `seed` (only missing items/fields, never
  overwrites edited content), imports seed assets.
- Connect Supabase data migration and RLS step include all new tables.

## 3. Global content

Content shared by many pages: header/footer texts, contacts, social links, legal line.

```ts
// src/content/globals/site.ts
export const siteGlobals = defineGlobal({
  id: 'site',
  label: 'Header & footer',
  sections: [
    defineSection({ id: 'contacts', label: 'Contacts', fields: {
      phone: f.text({ label: 'Phone', localized: false }),
      email: f.text({ label: 'Email', localized: false }),
      address: f.textarea({ label: 'Address' }),
    }}),
    defineSection({ id: 'social', label: 'Social links', fields: {
      links: f.list({ label: 'Links', of: { network: f.select({ options: [...] }), url: f.link() } }),
    }}),
  ],
  seed: { en: {…}, uk: {…} },
});
```

- Same storage pattern as pages (reuse `page_content`-style tables with a `kind`
  discriminator, or dedicated `global_content` + revisions; decide and record in DECISIONS),
  no route, no SEO.
- Admin: Pages → Site-wide group, same editor without the SEO tab.
- Site: `getGlobalContent('site', locale)` typed from the definition, fallback order as
  pages, cached with tag `global:{id}`. Layout components (header/footer) use it; saving
  revalidates every page that rendered it.
- `content:check` accepts globals without routes.
- Add an optional `f.email()` and `f.phone()` field (validated, `tel:`/`mailto:` helpers) if
  they keep the field system consistent; otherwise document using `f.text` with validation.

## 4. Forms

### 4.1 Definition

```ts
// src/content/forms/contact.ts
export const contactForm = defineForm({
  id: 'contact',
  label: 'Contact form',
  fields: {
    name: { type: 'text', required: true, max: 100 },
    email: { type: 'email', required: true },
    phone: { type: 'tel' },
    topic: { type: 'select', options: ['general', 'project', 'job'] },
    message: { type: 'textarea', required: true, max: 3000 },
    consent: { type: 'consent', required: true },
  },
  successRedirectPageId: undefined, // optional "thank you" page; otherwise inline success
});
```

Field types: `text`, `email`, `tel`, `textarea`, `select`, `checkbox`, `consent`. Field
labels, placeholders, help, select option labels, consent text (rich text with link), submit
label and success message are editable content per locale (the form appears in Pages →
Forms → "Texts" tab using the generated editor). Validation messages are UI strings
(`src/site/messages`), with core defaults.

### 4.2 Site component

- Core provides an unstyled, accessible form engine (`<SiteForm form="contact" …>` or a
  hook) that the project styles with its own primitives and tokens (no visual values in
  core).
- Works without JavaScript (server action + redirect back with status), enhanced with JS
  (inline validation, pending state, no full reload).
- Accessible: labels, `aria-describedby` errors, error summary focus, required markers.
- Spam protection without third parties: honeypot field, minimum fill time (signed
  timestamp token), DB-backed rate limit per IP hash and per form; optional Cloudflare
  Turnstile adapter behind a config flag (adds CSP sources automatically when enabled).

### 4.3 Server side

- Server action: validate with Zod derived from the definition, run spam checks, store, then
  deliver. Never log submission data or secrets.
- `form_submissions`: id, form_id, locale, data JSONB, page path, status
  (`new | read | archived`), delivery status per destination, ip hash, user agent family,
  created_at. Index `(form_id, status, created_at)`.
- Retention setting (Settings → Forms, default 12 months) with cleanup in the existing
  maintenance cron; "Delete" per submission (GDPR requests).

### 4.4 Delivery

Adapter interface with:

- `email` via Resend API or SMTP (env: `MAIL_PROVIDER`, `RESEND_API_KEY` or `SMTP_*`,
  `MAIL_FROM`); reply-to set to the submitter's email; plain, safe text email.
- `webhook` (POST JSON, HMAC signature header with `FORMS_WEBHOOK_SECRET`) for
  CRMs/Zapier/Make.
- `telegram` (env `TELEGRAM_BOT_TOKEN`; chat id configured in settings).
- `dev` (default in development): writes to `.data/mail/` so everything is testable without
  accounts.

Destinations per form are configured in Settings → Forms (admins): enable adapters,
recipient emails, webhook URL, Telegram chat id, retention. Secrets only in env, listed in
Security → Environment (masked) via the env catalog. If delivery fails, the submission is
kept with `delivery: failed`, retried on the next maintenance run, and shown in the inbox;
the visitor sees success once the submission is stored.

### 4.5 Admin

- Pages → Forms group: one entry per form with an unread count. Screen tabs: Inbox (table:
  date, name/email preview, status, delivery; filters; open submission; mark read; archive;
  delete; export CSV of the filtered set) and Texts (form copy editor per locale).
- Overview: a small "New submissions" card (count, link) placed in the tertiary area, not
  above the analytics KPIs.
- Permissions: managers read/mark/archive/export; delete and Settings → Forms are
  admin-only (add permissions to the central map). Audit log for status changes, deletes
  and exports.

## 7. Acceptance criteria (Playwright on a production build where possible)

### Collections

- [ ] Manager creates a post in `en`, saves as draft: not on the site, not in sitemap;
      staff preview works; visitor gets 404.
- [ ] Publishing makes it appear on `/blog`, on its page and in the sitemap within seconds,
      without a rebuild; the `uk` version falls back (or hides) per `missingTranslation`.
- [ ] Changing the slug redirects the old URL with 308.
- [ ] Concurrent edit conflict detected; revision restore works.
- [ ] Pagination works with real URLs; out-of-range page → 404.
- [ ] Deleting a post → 404 and removed from sitemap; audit log shows title.

### Global content

- [ ] Editing the phone in Pages → Site-wide updates header and footer on every page and
      locale as configured; other content unaffected.

### Forms

- [ ] Contact form submits without JS and with JS; validation errors are accessible and
      localized; success message shown.
- [ ] Honeypot or too-fast submissions are rejected silently; rate limit triggers.
- [ ] Submission appears in the inbox (unread count), dev adapter wrote the email to
      `.data/mail/`; webhook adapter sends a signed request (test server).
- [ ] Delivery failure keeps the submission with `failed` status and retries.
- [ ] Manager can read and export but not delete or open Settings → Forms (server-side
      check).

### General

- [ ] A v1.1.0-style project (no collections/globals/forms, array registry) builds and
      passes its tests after the merge.
- [ ] All gates pass in CI; `check:bundles` shows no admin code in site bundles; Lighthouse
      budgets still met on Home, a blog list and a post (report numbers).
- [ ] Main admin sidebar unchanged; new UI only under Pages and Settings.

When done, summarize what was built, decisions (link DECISIONS entries), migration steps
for existing projects, Lighthouse results, and known limitations.
